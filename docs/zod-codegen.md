# Zod codegen

`trpc-py codegen zod` emits a zod v4 module validating **procedure
inputs** — the same object shapes the `.d.ts` input types describe — so
frontend forms check the backend's rules before a request is ever sent.
One constraint source (your Pydantic models), checked twice: by zod in
the form and by Pydantic on the server.

```bash
trpc-py codegen zod --app server:router --out web/schemas.ts
# or keep it fresh on every save alongside the .d.ts:
trpc-py dev --app server:router --out web/app-router.d.ts --zod-out web/schemas.ts
```

From Python, the same output comes from `generate_zod(router)` —
`trpc_rs_py.zodgen.generate_zod`, re-exported from the package root.

## What it emits

Given a `RegisterInput` model and a `register(form: RegisterInput)`
mutation (from `examples/react-zod-form/`):

```ts
// Generated by `trpc-py codegen zod` from the Python router. Do not edit.
// Pydantic constraints with no Zod equivalent are marked `// dropped:` —
// see docs/codegen.md ("Zod schemas") for the full mapping table.
import { z } from "zod";
export const RegisterInput = z.object({
  username: z.string().min(3).max(20).regex(/^[a-z0-9_]+$/),
  email: z.string().regex(/^[^@\s]+@[^@\s]+\.[^@\s]+$/),
  age: z.number().int().gte(18).lte(150),
  newsletter: z.boolean().default(false),
});
// procedure 'registrations' takes no input
export const RegisterInput_2 = z.object({
  form: RegisterInput,
});
```

Three things to read in that output:

- **One `export const <Model>` per referenced Pydantic model** — the
  model's fields and constraints become a `z.object`.
- **One `export const <Proc>Input` per input-taking procedure** — its
  parameters as an object schema. The name is the procedure path in
  PascalCase with an `Input` suffix (`posts.by_id` → `Posts_by_idInput`);
  collisions get a numeric suffix (`RegisterInput_2` above).
- **A comment for no-input procedures** — `// procedure 'x' takes no
  input` — so every procedure is accounted for in the file.

Schemas cover **inputs only**. Procedure outputs are already described
exactly by the `.d.ts` (see [TypeScript codegen](codegen.md)); a server
response is not something the client validates, it is something the type
asserts — so no `Output` schemas are emitted.

## Constraint mapping (the short version)

`Field` bounds, `StringConstraints`, `Literal`, enums, unions,
`Optional`/defaults, lists, tuples, `dict`, discriminated unions, and
ISO temporals all map — `int` becomes `z.number().int()`, `ge=` becomes
`.gte()`, `StringConstraints(pattern=...)` becomes `.regex()`,
`X | None` becomes `.nullable()`, `= None` adds `.optional()`, other
defaults become `.default(v)`. The full table, including
`discriminatedUnion` detection and `timedelta` → `z.iso.duration()`, is
in [codegen — Zod schemas](codegen.md#zod-schemas).

Parity is tested end to end: `fixtures/zod-cases.json` records
Pydantic's verdict on `hypothesis`-generated values, and
`src/zod-parity.test.ts` asserts the generated schema's `safeParse`
agrees — plus `z.input`/`z.output` assignability to the router types.

## Limits: what does not map

**Hard `TypeError`** (the same refusal set as `generate_types` —
the module is not written): unannotated parameters, `**kwargs`,
`RootModel`, computed fields, serializer metadata, and annotation
shapes without an exact JSON mapping. See
[codegen — hard failures](codegen.md#hard-failures-instead-of-any).

**`// dropped:` comments** where a constraint has no zod equivalent —
the schema still validates, just without that check:

- `StringConstraints(strip_whitespace=True)` (also `to_lower`,
  `to_upper`, `strict`) and other string transformations
- `default_factory` and non-JSON defaults (field becomes `.optional()`)
- Unrecognized non-Pydantic `Annotated` metadata classes.

**Pydantic-internal metadata is skipped silently** — it never reaches
the generator at all:

- `Field(pattern=...)` — put regexes in `StringConstraints(pattern=...)`
  if they belong in the form check (this is why `react-zod-form` uses
  `StringConstraints`).
- Custom validators (`@field_validator`, `AfterValidator`, …) — the zod
  schema applies the *structural* contract; your custom checks still run
  server-side.

**Documented divergences**, where the two validators disagree by design:

- **Strict vs lax.** Pydantic's default lax mode accepts `"30"` → `int`
  or `True` → `int` at runtime; zod is strict and rejects them. The
  schema is stricter than the server, which is the safe direction for
  forms — a zod-accepted payload is always server-valid, but the
  converse can fail for coerced values.
- **Python-only regex constructs** (`\A`, `\Z`, `(?P<name>…)`) do not
  translate; other patterns emit verbatim with `/` escaped.
- `z.iso.*` validates a narrower set of ISO strings than Pydantic
  accepts in some edge cases.

## Pairing with form validation

The point is one rulebook. `RegisterInput.safeParse(values)` in the form
produces per-field issues before submit; whatever slips past — say, a
payload assembled by hand — is still rejected by Pydantic server-side
and surfaces through the tRPC error envelope as `BAD_REQUEST`:

```ts
const parsed = RegisterInput.safeParse(form);
if (!parsed.success) {
  showFieldErrors(parsed.error.issues);
  return;
}
trpc.register.mutate({ form: parsed.data });
```

`examples/react-zod-form/` is the runnable version: a Vite + React form
using `@trpc/react-query`, the generated `app-schemas.ts`, and a
`generate_types.py` that regenerates both the `.d.ts` and the schemas.
Wire `--zod-out` into `trpc-py dev` and the schema module tracks your
Python edits exactly like the `.d.ts` does — see
[live type sync](live-type-sync.md).
