Latest run: **0.8.0** (see `benchmarks/results/0.8.0/` for the raw JSON —
reproduce with `uv run python benchmarks/run.py`). Criterion micros and
the full oha matrix run back-to-back in one process, so absolute numbers
shift with machine load between runs — compare ratios between rows in one
version, not totals across versions. The security work in 0.8.0
(`procedure_timeout`, audits, fuzz harness) adds no per-request cost when
the timeout is unset.

## HTTP load (oha)

Four workloads per server: a single query, a 10-call batch in one HTTP
request, a mutation, and a 100 KB payload.

| Server | single query | batch of 10 | mutation | 100 KB payload |
| --- | --- | --- | --- | --- |
| trpc-fastapi | 10,206 req/s (p99 2.83 ms) | 5,351 req/s (p99 8.53 ms) | 9,932 req/s (p99 3.80 ms) | 3,348 req/s (p99 12.31 ms) |
| trpc-standalone | 7,398 req/s (p99 4.03 ms) | 5,228 req/s (p99 5.37 ms) | 6,716 req/s (p99 5.00 ms) | 4,637 req/s (p99 6.02 ms) |
| plain FastAPI | 5,677 req/s (p99 8.11 ms) | 6,179 req/s (p99 3.99 ms) | 6,481 req/s (p99 7.30 ms) | 2,132 req/s (p99 17.22 ms) |
| Node `@trpc/server` | 24,378 req/s (p99 2.08 ms) | 13,355 req/s (p99 2.98 ms) | 24,546 req/s (p99 1.92 ms) | 7,253 req/s (p99 4.82 ms) |

![Requests per second by workload and server](/benchmarks/latest-http-rps.svg)

![p99 latency by workload and server](/benchmarks/latest-http-p99.svg)

Reading: across three runs (0.7.0 quiet, 0.7.0 release, 0.8.0
release) the consistent pattern is that **the standalone Rust server
dominates on writes and large bodies** — here ~1.4–2.2x over plain
FastAPI and ~1.4x over the uvicorn mount on the 100 KB payload — while
single-query ordering between the two Python transports moves with
machine load. The tRPC mount remains ~1.8x a plain FastAPI JSON view on
single queries because parsing and serialization happen in the Rust
core. The official Node adapter still leads on small requests — Python
handler dispatch dominates there.

## Adapter micro-benchmarks (pytest-benchmark)

| Benchmark | median |
| --- | --- |
| tRPC query through the ASGI mount | 1,011.5 µs |
| Plain JSON view baseline | 1,009.0 µs |
| tRPC query through `mount_wsgi()` (Flask) | 1,703.8 µs |
| tRPC query through `trpc_view()` (Django) | 1,677.5 µs |
| `generate_types`, 10 procedures | 148.7 µs |
| `generate_types`, 50 procedures | 812.5 µs |
| `generate_types`, 200 procedures | 3,259.1 µs |

![Python adapter and codegen micros](/benchmarks/latest-python-micro.svg)

The ASGI adapter stays within noise of a plain JSON view (1,011.5 vs
1,009.0 µs); the WSGI and Django adapters still cost roughly **0.7 ms
per request** — the price of the pumped event loop and worker-thread
bridge that lets the shared ASGI dispatch (including SSE streaming) run
inside a synchronous framework; see [adapters](/docs/adapters) for the
operational limits this implies. Codegen scales roughly linearly —
~3.3 ms for a 200-procedure router — leaving large headroom under the
1-second save-to-`.d.ts` target that `trpc-py dev` operates under.

Protocol parsing and serialization are nanosecond-scale; per-request cost
is dominated by HTTP handling and Python dispatch, not the protocol core.

## Deferred until the features exist

- SSE / streaming-subscription load: benchmarks for long-lived streams
  (throughput per client, memory per connection) are planned for a later
  milestone; subscriptions have functional coverage only.
- Rust-side codegen benches: codegen is Python today.
- Pure-Python protocol comparison and WSGI/Django `oha` baselines: still
  deferred — the 0.7.0 performance pass prioritized the standalone-vs-
  uvicorn comparison, which was the decisive question for this release.
